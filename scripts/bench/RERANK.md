# 重排参考实现与会话证据预算

2026-10-30。生产基线为 `a3e2709`。本轮完成官方 Python 模型的离线评分与真实
`contextpack.Build` 回放，并另外修复“同会话最多两条”的硬限制。重排没有接入或
部署到 MemSpace 服务，embeddings.cpp 也尚未增加分类推理。

## 84.8% 是什么成绩

这是我们 100 道合成回归题中的 **67/79 正例可见证据找齐**，不是公共数据集成绩。
1 道全项目题不做自动注入，另有 20 道空证据标签。题集很小、主要为短编码记录，
且所有旧测试题已经被检查过；只能说明本次回归改善，不能推断竞品排名。

例如 [agentmemory 官方报告](https://www.agent-memory.dev/benchmarks) 的 84.7%
是 LongMemEval-S 的 398/470，要求前五个不同**会话**包含全部标准来源，测的是
BM25 组件，不运行捕获、压缩、向量或回答模型。我们的单位、语料、预算、可见短语
检查都不同。它的相近数字不能拿来判断我们已达到同一水平。

## 官方 Python 重排对照

模型 `BAAI/bge-reranker-v2-m3`，revision
`953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e`，CPU float32、6 线程、batch 4、
问题与原文合计最多 512 tokens。权重 SHA256 经校验；没有训练或调用聊天 LLM。

先冻结真实搜索在深度 12/24 的候选，保留范围过滤和 SearchFloor 0.45。推理只读
问题、来源原文，读不到答案标签。742 个不同文本对评分；其中 10 对有截断，最长
原始输入 539 tokens。然后在独立 worktree 中用真实 Build 回放不同策略，保持来源
读取、会话分组、总条数和字符预算。初次回放仍使用基线的两条上限。

候选深度、策略与原始 logit 门槛 -4/-2/0/2/4/6 在评分前固定。只用 dev 选择：
不损失已有 dev 通过题、不新增 dev 明确负例非空，优先找齐，其后优先少注入文本。
选中的是 **深度 12、rescue、logit >= -2**：原规则允许的保留，重排额外允许的补入。
新分数不是概率，也不是可以直接沿用的 cosine 门槛。

| 项目 | 原策略 | dev 选中的补救策略 |
|---|---:|---:|
| dev 正例 | 23/26 | 25/26 |
| test 回归正例 | 34/53 | 42/53 |
| 全部正例 | 57/79，72.2% | 67/79，84.8% |
| 明确负例非空 | 2/12 | 2/12 |
| 缺失属性/核对前提题非空 | 8/8 | 8/8 |
| context token p50 / p95 | 125 / 488.2 | 135 / 488.2 |

新增找齐 q002、005、011、016、018、025、026、027、039、052，无已有正例退步。
仅换排序而保留旧注入门槛，仍为 57/79；直接用新门槛替换旧规则、同样阈值 -2，
为 62/79。保留原规则再补救在该回归集上更稳。

**非空负例数量没增加，不代表无关片段没增加。** 手动复核发现“版本回滚”题还带入
日志轮转、DNS 记录，“dependency injection”题还带入集成测试记录；q078、q097
原有错误主题返回也没有修好。现有证据标签只标必须包含的来源，并非完整相关性
标注，不能据此计算可靠的 precision 或宣布噪声不变。

网格中的阈值 -4 达到 71/79（89.9%），但 dev 找齐仍为 25/26，注入总字符从
46,515 增至 56,012，约多 20%。原选择规则因此取 -2。不能看完 test 后悄悄挑更高
数字、再当作独立验证收益；这两个工作点需更多相关性标注和新题来取舍。

## 更宽候选没有解决什么

参考 [Hindsight 的候选与最终预算分离](https://hindsight.vectorize.io/developer/api/recall)
以及[独立的语义候选门槛](https://hindsight.vectorize.io/developer/configuration)，另外测试
候选 SearchFloor 0.30、深度 12/24/48。仅改变实验 runner，不修改服务阈值；保留
上一步的补救策略及 -2 门槛，不重新按 test 选参数。

三个深度仍均为 **67/79**，明确负例非空仍为 2/12。深度 48 使协程泄漏、序列化
丢字段等正确来源进入候选，但模型给它们低于 -2 的分数，仍未接纳；前端状态管理的
正确来源仍没进入这个候选池。更宽检索本身不能保证更完整。

题集每条记录附带相同的通用 prompt，某些查询中重复 prompt 占满前排候选，导致
正确来源出现在第 13、38、42 名。这是夹具放大的问题，不代表真实库中存在同样的
重复比例。需要测试检索前的重复内容处理、分路候选配额，以及中英短问题的召回和
分数校准，而不是只加最终条数。

宽候选共产生 1,580 个不同文本对，复用已验证的 742 对中的 742 对，新增 838 对。
同一 query/ref 在不同候选深度可能命中不同 chunk，因此最终缓存按深度隔离，推理
缓存按 query+原文隔离。首个宽候选尝试因该冲突明确失败，不计为有效实验；修正后
才完成回放，并补了防止跨 chunk 混分的测试。

## CPU 开销

16 道预先固定的长短、负例及空结果探针，各重复 3 次，模型常驻，不跨请求复用分数：

| 候选深度 | 请求样本 | 模型调用 p50 / p95 | 单模型调用超过 1.5 秒 |
|---|---:|---:|---:|
| 12 | 48 | 0.860 / 4.622 秒 | 9/48 |
| 24 | 48 | 1.314 / 4.663 秒 | 12/48 |

包括 Python 分词和 CPU 推理，排除检索、HTTP、打包、排队和启动；探针刻意覆盖
长文，不是完整题集的生产 p95。当前 hook 总 deadline 1.5 秒，因此该配置不能直接
接入。还应测试只重排有歧义的候选、更好的长度分桶、小模型或量化；不能假设移植
C++ 就一定满足预算。模型进程 RSS 本轮未单独测量。

## 两条是否太少：另加专项测试并修复

两条是**每会话**限制，prompt 总量原本就是最多六条。剩余 12 道旧漏题的标准来源
不共享会话，因此不是这个限制导致；但它确实挡住需要同会话三条以上证据的新场景。

新增 [session-budget-v1.json](data/session-budget-v1.json)：四个项目、16 条来源、
8 道要求同会话 3 或 4 条的题。相同主题词刻意消除检索难度，只测打包容量。
它不是新的独立检索 benchmark，不与旧 100 题合并制造更高总分。

| 专项指标 | 固定每会话两条 | 预算内补齐 |
|---|---:|---:|
| keyword search 找齐 | 8/8 | 8/8 |
| context / 首次 hook 找齐 | 0/8 | 8/8 |
| 首次 hook token p50 / p95 | 187 / 187 | 309 / 309 |
| 即刻重复 hook 非空 | 0/8 | 0/8 |

每题重复 3 次，两版各 96 条回执。旧源码快照与 `a3e2709` 逐字节一致。
修复移除每会话硬截止，保留现有 round-robin：先覆盖不同会话，再轮流补入额外合格
来源，仍进行内容去重，仍最多六条、6000 字符。它不会自动判断“恰好需要几条”。
原 100 题再跑 3 次，1803 条评分全部不变，仍为未接重排的 57/79；没有把 Python
回放的 84.8% 冒充已部署能力。新增测试还验证一个会话四条不会挤掉另外两个会话。

## 别家源码中值得借鉴的实现

agentmemory 固定 commit `c6c476d2905926727fa5848a134d7a3b38a7fa98`：

- [每会话默认三条、未填满时回填](https://github.com/rohitg00/agentmemory/blob/c6c476d2905926727fa5848a134d7a3b38a7fa98/src/state/hybrid-search.ts#L293)：是软配额；本轮借鉴其思路修复我们的硬限制，并非照搬常数三。
- [更宽召回再重排](https://github.com/rohitg00/agentmemory/blob/c6c476d2905926727fa5848a134d7a3b38a7fa98/src/state/hybrid-search.ts#L99)：候选与最终返回条数分开，不等于最终注入所有候选。
- [MiniLM 重排、q8、完整失败回退](https://github.com/rohitg00/agentmemory/blob/c6c476d2905926727fa5848a134d7a3b38a7fa98/src/state/reranker.ts)：部分候选评分失败就保留原排序，避免混用半批 logits 与融合分数。该模型不能未经中英评测直接照搬。
- [上下文按预算装入](https://github.com/rohitg00/agentmemory/blob/c6c476d2905926727fa5848a134d7a3b38a7fa98/src/functions/context.ts#L265)：不合适的块放不下时继续尝试后面的块。该上下文接口、混合搜索及可选重排均不是其 84.7% BM25 组件 benchmark 的实测配置。

[MemReranker 论文](https://arxiv.org/html/2605.06132v2) 还专门讨论“主题相近但不包含
答案”、跨表达匹配和分数校准问题，标签区分实体/属性、完整性、信息密度。可借鉴
其评测与标注维度；本轮未运行该模型，也不把其自报延迟当本机结果。

后续优先级：补新题和完整相关性标注；清理重复候选占位；为中英短查询验证改写或
合适的重排；按问题所需的决策、实施、验证、恢复证据组合选择。数量软配额只是
解除容量限制，不能替代这些相关性和完整性判断。
