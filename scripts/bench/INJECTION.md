# 注入链路诊断与修复

后续：本文所记录的后台批次排队超时已完成修复，并更新本机嵌入服务，见 [TIMEOUT.md](TIMEOUT.md)。本页保留注入修复阶段的质量对照与当时的服务波动记录。

2026-10-30。在原来的 coding-v1、80 道题上定位 38.0% 的可见证据找齐率。本轮不改语料、标注、模型、搜索融合、相似度阈值或字符总预算。

## 根因与改动

1. **短中文查询被跳过。** hook 和 context builder 各有一份“至少 6 个字母或数字”的规则。6 道正例根本没发起召回，包括“协程泄漏”“证书过期”“版本回滚”。统一到 `prompt.ShouldRecall`，允许紧凑的汉字查询，同时跳过“好的”“继续”等低信息输入。原先短查询获准检索后仍可能因召回/相似度失败，不能把这 6 题全算作修复增益。
2. **关键词门槛覆盖了强语义信号。** RRF 融合保留 keyword 的 `Match=any` 标记，即使同一来源的 semantic similarity 已达 0.60，原有逻辑仍仅按关键词覆盖率拒绝。改为关键词条件或强语义条件满足任一即可。语义注入阈值仍是 0.60，搜索下限仍是 0.45。
3. **把展示 snippet 当成了证据正文。** FTS 的短展示片段可能只留下问题和现象，再次按 300 bytes 截断对中文更不利。对已通过相关性筛选的来源，重新按 owner、project、doc_id 查询派生搜索正文；不超过 600 个字符时保留完整正文。长正文仍用聚焦 snippet，整个 pack 仍按原字符预算裁剪。保留脱敏、wrapper 中和、来源标注与去重。
4. **会话去重可能只留下问题。** 新增的独立回归例发现：短问题经常比同会话的较长答案排名更高，原规则只保留问题。改为保留会话原始排序，但当同会话存在独立通过相关性筛选的答案、失败或摘要时，用它替代 prompt。没有合格后续证据的用户决策 prompt 仍可保留。这个场景由新增回归测试覆盖，原 80 题的通用 prompt 夹具不能证明其真实收益。

修复前的诊断记录了缺失证据来源的拒绝原因：短查询 6、强语义被关键词门槛覆盖 11、弱语义阈值 14、关键词覆盖率 3、候选遗漏 3、可见事实缺失 9。这是 **46 条缺失来源/备选来源**，多个来源可属于同一题，不能相加当作失败题数。

## 同输入的质量对照

实时复测中，共享嵌入服务在 1s deadline 下发生超时并触发熔断，两次完整 live 运行因此混入大量关键词降级。不能把这些运行当作正常 hybrid 的质量对照，也不能把低延迟误读为优化效果。

为隔离服务可用性，先由真实 bge-m3 服务逐条生成并冻结查询向量，再复用这些向量运行**原代码**与**修复后代码**。文档仍经生产分块/嵌入，查询仍经生产 KNN、scope、阈值、RRF、context builder 和 loopback hook。没有 fake 向量，也没有放宽阈值。此模式仅用于质量与注入体积，**不报告线上延迟或可用性提升**。

原代码在独立 detached worktree 中运行，确认其 `contextpack.go` 和 `inject.go` 与原始 HEAD 完全一致。两边各跑 80 题、3 次；query snapshot、语料与模型指纹相同；所有 search 模式的来源顺序及 similarity 逐条一致。

## 真实干扰复核

在相同冻结查询向量下，再加入原先固定的 200 条真实干扰文档，每条取前 400 个字符（共 520 个搜索文档）。修复后首次 hook 找齐仍为 49/71（69.0%），负例误注入仍为 1/8，scope 越界、来源标注错误与重复输出均为 0。token p50 / p95 为 122 / 301.8。

此组仅复核修复后在有限噪声下的表现，没有为噪声组重新跑一次旧代码的受控重放；原始 live 噪声基线为 27/71、无降级。干扰来源未标注全部等价事实、项目归属经重映射且正文已截断，不能外推完整真实库表现。

## 剩余问题

剩余 22 道正例未找齐：15 道相关来源未达 0.60 的语义注入门槛，3 道弱语义且关键词覆盖不足，4 道相关来源未进入当前候选。比如英文 “why are sign-ins slow” 找到正确来源，但 similarity 约 0.591；“协程泄漏”现在能发起召回，但相关英文记录仍未进入候选。

这 22 题不再是“已选齐引用但正文丢失了标注事实”。不继续凭这一小批正例降低阈值；后续需要更多近义但无关、跨语言和技术标识符负例来校准精度/召回取舍。

共享嵌入服务的超时/熔断也仍是独立的实际问题：此次质量修复没有解决 live 可用性。逐题记录现在保留 `semantic.last_error`，便于下一步区分服务拥塞与注入逻辑问题。代码尚未部署到当前运行服务。
